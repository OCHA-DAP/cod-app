<ProcessDetail cell="step-1-ocha-hq-with">

- Starts the review twice a year, or as often as the WG decides.
- Sends review requests to the IMWG. The email links to the [COD-AB Request Form](../request/) and, where available, to optional tools.
- Maintains the form. Anyone can open it without logging in, but it is shared only within the COD-AB group, the IMWGs and, by email, with Member Agency Country Teams.

</ProcessDetail>

<ProcessDetail cell="step-1-ocha-hq-without">

- Starts the review twice a year, or as often as the WG decides.
- Maintains the [COD-AB Request Form](../request/). Anyone can open it without logging in, but it is shared only within the COD-AB group, the IMWGs and, by email, with Member Agency Country Teams.

</ProcessDetail>

<ProcessDetail cell="step-1-agency-hq-without">

- Sends review requests to its country teams. The email links to the [COD-AB Request Form](../request/) and, where available, to optional tools.

</ProcessDetail>

<ProcessDetail cell="step-1-imwg-with">

- Reviews the current COD-AB on HDX.
- Submits the [COD-AB Request Form](../request/) as **Change** or **No change**.

</ProcessDetail>

<ProcessDetail cell="step-1-agency-country-without">

- Reviews the current COD-AB on HDX.
- Submits the [COD-AB Request Form](../request/) as **Change** or **No change**.

</ProcessDetail>

<ProcessDetail cell="step-2-ocha-hq-with">

- Reconciles the submissions for each location.
- Creates one ticket in the ticketing system (Jira) and one shared storage folder (SharePoint) per location, and notifies all Member Agency HQs, tagging the relevant representative and alternate.
- If needed, splits the request to match the admin level 0 master list, with one root folder per state, territory or disputed territory.
- Prepares sources, or delegates this to the IMWG:
  - For government data, a fact-finding consultation establishes admin levels, units per level, unit names, government P-codes and boundary geometries, with official sources linked and evidence recorded on the work order. Gaps are noted but do not stop the process.
  - For non-government data (when government sourcing failed, in an emergency, or when there is no viable partner), fact-finding is shortened or skipped and the reason recorded.
  - Checks the geometry (for example WGS 84) and the codes and names (unique, non-empty, with parent codes), and cleans them so sources can be compared.

</ProcessDetail>

<ProcessDetail cell="step-2-ocha-hq-without">

- Reconciles the submissions for each location.
- Creates one ticket in the ticketing system (Jira) and one shared storage folder (SharePoint) per location, and notifies all Member Agency HQs, tagging the relevant representative and alternate.
- If needed, splits the request to match the admin level 0 master list, with one root folder per state, territory or disputed territory.
- Asks the Member Agency HQ to upload geodata, supporting documents and the checklist to the shared storage.

</ProcessDetail>

<ProcessDetail cell="step-2-agency-hq-without">

Prepares sources, or delegates this to its country team:

- For government data, a fact-finding consultation establishes admin levels, units per level, unit names, government P-codes and boundary geometries, with official sources linked and evidence recorded on the work order. Gaps are noted but do not stop the process.
- For non-government data (when government sourcing failed, in an emergency, or when there is no viable partner), fact-finding is shortened or skipped and the reason recorded.
- Checks the geometry (for example WGS 84) and the codes and names (unique, non-empty, with parent codes), and cleans them so sources can be compared.
- Uploads geodata, supporting documents and the checklist to the shared storage when OCHA HQ asks.

</ProcessDetail>

<ProcessDetail cell="step-2-wg-without">

- Agrees which member agency leads the update. If only one agency provided data, that agency should lead.

</ProcessDetail>

<ProcessDetail cell="step-3-imwg-with">

- Coordinates the review with other relevant stakeholders, comparing the sources with the current COD-AB.
- Endorses and nominates one source as the Candidate, or decides not to update.
- Informs OCHA HQ of the outcome.

</ProcessDetail>

<ProcessDetail cell="step-3-lead-without">

- Coordinates the review, which the Member Agency Country Teams carry out with other relevant stakeholders.
- Nominates one source as the Candidate, or decides not to update.
- Informs OCHA HQ of the outcome.

</ProcessDetail>

<ProcessDetail cell="step-3-agency-country-without">

- Carries out the review with other relevant stakeholders, comparing the sources with the current COD-AB.

</ProcessDetail>

<ProcessDetail cell="step-3-ocha-hq">

- Records the outcome in the ticketing system.
- If there is no update, closes the ticket.

</ProcessDetail>

<ProcessDetail cell="step-4-ocha-hq-with">

Can delegate this work to the IMWG.

- Fixes geometry and topology, edge-matches to the agreed admin level 0, applies the P-code standard schema (field names and types, including language and date fields) and generates new P-codes.
- If the country asks, also keeps non-edge-matched versions as `_src` files.
- Validates six areas: schema and geometry, topology, P-codes, national codes, naming, and language and date fields. All must pass.
- Does the checks that cannot be automated: transliteration, naming across layers, and name validity against government documents.
- On any issue, sends the Candidate back to Step 3.
- Uploads the Candidate to `2_Candidate` in an open geospatial format (for example GeoPackage or GeoJSON), with the completed metadata template and quality checklist.

</ProcessDetail>

<ProcessDetail cell="step-4-lead-without">

Can delegate this work to its country team.

- Fixes geometry and topology, edge-matches to the agreed admin level 0, applies the P-code standard schema (field names and types, including language and date fields) and generates new P-codes.
- If the country asks, also keeps non-edge-matched versions as `_src` files.
- Validates six areas: schema and geometry, topology, P-codes, national codes, naming, and language and date fields. All must pass.
- Does the checks that cannot be automated: transliteration, naming across layers, and name validity against government documents.
- On any issue, sends the Candidate back to Step 3.
- Uploads the Candidate to `2_Candidate` in an open geospatial format (for example GeoPackage or GeoJSON), with the completed metadata template and quality checklist.

</ProcessDetail>

<ProcessDetail cell="step-5-wg">

- Reviews the standardized Candidate.
- Can return it to Step 4 for rework.
- Must accept it, as must the in-country reviewers, before Step 6.

</ProcessDetail>

<ProcessDetail cell="step-5-imwg-with">

- Reviews the standardized Candidate.
- Can return it to Step 4 for rework.
- Must accept it, as must the WG, before Step 6.

</ProcessDetail>

<ProcessDetail cell="step-5-agency-country-without">

- Reviews the standardized Candidate.
- Can return it to Step 4 for rework.
- Must accept it, as must the WG, before Step 6.

</ProcessDetail>

<ProcessDetail cell="step-6-ocha-hq">

- Packages adm0 to adm4 polygons and boundary lines (and optionally the same for the non-edge-matched version), admin points and admin capitals.
- Completes the Metadata Worksheet, the single source of truth that both ArcGIS Portal and HDX read from.
- Imports the data and metadata into the SQL Enterprise Geodatabase, which keeps every version with one active at a time.
- Runs the Pre-Publication Checklist (supplemental layers, metadata completeness, readiness), runs validation again, and gives the final sign-off.
- Publishes: an authorized team member runs the publication script, which overwrites the main Portal layer, publishes a new versioned layer, and deprecates prior versions while keeping them available. HDX picks up the data automatically.
- Once the data is live on HDX, sends a notice from OCHA's shared COD inbox to the country or regional office and to Member Agency HQs.
- Closes the work order once both the ArcGIS Portal and HDX updates are live. Errors found later start a new work order.
- Informs the UN Geospatial Section of the new version.

</ProcessDetail>

<ProcessDetail cell="step-6-partners">

- The UN Geospatial Section (UNGIS) is informed of each new version, so that it can start the official endorsement process under UN procedures (UN-GGIM and SALB). That decision rests with UNGIS and is outside this process.
- Other stakeholders hear of the update through various channels.

</ProcessDetail>

<ProcessDetail cell="step-ongoing-ocha-hq">

- Keeps the ticket in the ticketing system as the status record for each update.
- Where available, keeps a live [COD-AB status dashboard](../../../status/), fed from the work order system, showing for each location the status, last update, open issues, responsible people and dataset links.
- Automated notifications go out at each status change (opened, under evaluation, in cleaning, ready for finalization, published to Portal, published to HDX, completed).

</ProcessDetail>

- Watches administrative boundaries and submits a new update form when they change.

</ProcessDetail>
